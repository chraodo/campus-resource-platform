# 工程伦理与风险处理

本文把伦理要求落实到产品规则和团队流程中。当前没有对学生、管理员或维修人员进行访谈；下面的安排是项目方案，不是用户已认可的结论。组员需要在启动评审中确认哪些对象需要进一步征询。

## 可能受影响的人

学生会用系统安排学习空间；审批人员要决定整间教室的使用；维修人员会接触故障位置和报修信息；学校管理员会看到资源使用和操作记录。预约记录和签到结果可能反映个人到场情况，因此需要限制收集和查看。

## 风险、措施和待确认项

| 风险 | 可能造成什么后果 | 当前设计 / 后续需确认 |
| --- | --- | --- |
| 预约与签到记录泄露 | 暴露个人学习时间和地点 | 学生默认只能查看本人预约；管理员和屏幕凭证权限分开；屏幕令牌只对应一个房间；需要小组确认审计/预约记录保留多久 |
| 未签到自动记违约 | 迟到、断网或无法使用签到屏幕的人可能受到不公平影响 | 系统仅记录一次未签到，不自动累计处罚；必须向老师确认申诉、复核、免责和人工纠错流程后，才决定是否扩展规则 |
| 屏幕签到码被转发 | 他人可能替签到 | 代码按房间和日期生成，屏幕令牌只读对应房间，使用后校验本人有效预约；仍需实地测试屏幕可见范围和轮换策略 |
| 部门专属空间筛选错误 | 学生被排除在本可用空间之外，或看到不该访问的信息 | 后端查询按账号院系控制；应由不同院系账号做权限验收；管理员维护归属时要能纠错 |
| AI 误解请求或越权 | 错误预约、取消或报修 | 自然语言 Agent 是可选项；若实现，先追问缺失条件、写操作先展示摘要并取得明确确认，后端重新检查权限；无确认不得执行 |
| 邮箱配置或投递错误 | 消息发给错误收件人或泄露预约信息 | 邮箱字段可空；演示使用虚构数据；生产启用前确认收件人、内容范围和用户如何修改/删除邮箱；不要将 SMTP 密钥写入代码 |
| 自动化偏差不易发现 | 学生长期被不一致地限制或维修优先级不公平 | 规则应公开；运营统计按必要范围汇总；记录决策原因，提供人工复核方式，并检查不同空间/群体的异常差异 |
| 依赖/权限配置错误 | 未授权者改数据或服务停止 | 服务端 RBAC、最小权限、迁移前备份、CI 检查和回退步骤；部署凭据由实际负责人保管 |

## 数据最小化建议

- 只收实现预约、申请、报修和授权所需的信息；不收与空间服务无关的学生资料。
- 工单标题/描述提示用户不要填写身份证号、健康信息等敏感内容。
- 审计记录保留操作者、动作、对象、时间和必要原因；不记录密码、邮件正文之外的无关聊天内容或凭证。
- 演示和自动化测试始终使用虚构账号、地点和报修数据。
- 课程展示结束后，由小组确认如何清理本地演示库、测试邮件和访问令牌。

## 小组必须补上的真实伦理工作

启动评审记录谁负责向老师/场地管理人员确认数据保留、未签到申诉、部门空间边界和邮件通知范围。每名组员的个人伦理分析应基于其真实讨论、审查或测试经历；本文件不能代写个人经历或声称已经完成实地评估。
