# 校园资源服务平台详细需求基线

> 依据《课程实践项目（PJ）任务书》整理。本文把任务书要求拆成可讨论、可追踪、可验收的条目。代码实现、自动化测试通过、组员人工验收和课程评审是四件不同的事；下文所写的实现状态以 PR #1 的代码为准，尚待组员确认。

## 1. 项目目标与边界

系统面向校园自习空间，覆盖座位预约、整间教室申请审批、空间报修，以及这三类业务共同依赖的账号权限、空间目录、通知和审计。

### 1.1 必做范围

- **M1 自习座位预约**：搜索、预约、签到、未签到释放和违约记录、历史查询与原座复约。
- **M2 整教室预约与审批**：提交申请、多级审批、驳回、超时撤销；只有最终批准后占用教室。
- **M3 物业报修**：上报、派单、维修中、超时升级、完工验收和评价。
- **D 公共层**：基于 RBAC 的身份和权限、空间与座位主数据、通知服务、操作审计。
- **跨模块集成**：M2/M3 对 M1 的资源状态产生影响；查询时能追溯状态来源。
- **工程交付**：需求基线、项目规则、提交与 PR 审查、流水线、迁移、测试环境、生产审批和回退记录。

### 1.2 附加范围

自然语言业务 Agent 是附加项，不是上述必做模块的前置条件。只有小组决定交付时，才需要验证追问不完整意图、调用公开接口、写操作先确认，以及将安装和配置纳入流水线。DSH 是任务书建议的接入方式之一，不是核心平台的依赖。

## 2. 用户与权限角色

以下是当前代码提供的角色示例，最终角色划分、权限和真实负责人由小组确认。权限必须由服务端检查，页面上隐藏按钮不能代替后端校验。

| 角色 | 主要操作 | 不应默认拥有的权限 |
| --- | --- | --- |
| 学生 | 查座位、预约/取消本人座位、签到、提交/查询本人教室申请、报修和验收本人维修 | 管理全校账号、修改空间主数据、查看他人预约 |
| 一级审批人 | 查看申请、处理当前的一级审批 | 执行二级审批，除非额外授予权限 |
| 二级审批人 | 查看申请、处理当前的二级审批 | 执行一级审批，除非额外授予权限 |
| 维修人员 | 查看工单、认领/处理被派工单 | 修改账号、空间主数据或查看与职责无关的业务信息 |
| 空间管理员 | 管理空间和座位、查看空间使用情况 | 默认修改审批结果或学生身份 |
| 运营管理员 | 查看运营统计及被授权的预约/工单信息 | 默认创建或变更业务记录 |
| 系统管理员 | 账号、角色、权限和系统配置管理 | 不得跳过审计或把共享规则改成无记录的隐式状态 |

权限码应从服务端权限目录中选择。自定义角色只能包含已登记的权限码；停用角色后，该角色账号不得继续通过旧会话执行需要该角色权限的操作。

## 3. M1：自习座位预约

### M1-01 搜索可用座位

使用者可以按日期、开始时间、预约时长、区域以及电源/无障碍等座位属性筛选。

**验收条件**

1. 只返回启用的空间和座位；院系专属空间仅对本院系用户和获准管理者开放。
2. 开始时间按整点选择；暂不支持跨日预约。
3. 查询结果给出可预约状态。不可预约时，应说明是开放时间、个人预约、教室审批占用还是维修占用，并给出来源模块和来源单号。
4. 查询的可预约结果只是当时的状态；提交预约时必须再次由服务端校验。

### M1-02 创建、取消和幂等

学生选定一个可用座位和时间段后提交预约。任务书要求整点小时为单位，单次最多 4 小时且系统参数可调；当前实现默认 4 小时，管理员参数范围为 1–24 小时，实际运行上限需小组确定。

**验收条件**

1. 服务端检查用户权限、空间访问范围、座位/空间状态、开放时间、预约时长和时间范围。
2. 冲突区间按半开区间判断：新预约开始时间早于已有占用的结束时间，且新预约结束时间晚于已有占用的开始时间，才算重叠；首尾相接不算重叠。
3. 已被有效 M1 预约、M2 教室占用或 M3 维修占用的资源不能被再次预约。
4. 幂等键在同一用户范围内唯一。相同键和相同请求重试应返回同一预约；相同键对应不同请求应拒绝。
5. 学生只能取消本人预约；管理员权限按服务端权限明确授予。
6. 取消或超时释放后，历史和审计信息保留，不物理删除预约记录。

### M1-03 签到和未签到释放

学生到达预约空间后，通过 Web 输入当天房间动态码签到。房间屏幕令牌只用于对应房间，不得作为普通账号令牌使用。

**验收条件**

1. 动态码由服务端按房间和日期生成；屏幕接口限制缓存；预约接口不返回动态码。
2. 只有预约本人或明确获授权的管理者可处理签到。
3. 预约开始前 15 分钟提醒；开始后 10 分钟仍未签到再次提醒；开始后 15 分钟仍未签到时释放座位、记录一次违约并通知学生。
4. 已签到后不应再收到迟到提醒或未签到处罚。
5. 重复运行定时任务不得重复生成同一提醒、违约记录或审计事件。
6. 目前邮件代码可接 SMTP；真实学校邮箱和微信渠道尚未确认或实测。没有 SMTP 时，站内通知仍应可用。

### M1-04 历史复用与运营管理

学生能查看自己的预约历史，并从历史记录定位到原座位，再选择新的日期和时间确认预约；历史记录不能直接变成新预约。

管理员可以管理空间、座位、开放时间和系统预约参数；获准的运营人员可以查看预约情况和统计数据。

**验收条件**

1. 历史预约只对本人可见；运营视图按已授予的权限开放。
2. 复约时必须重新执行搜索和冲突校验，界面需让学生核对日期、时长和座位。
3. 修改开放时间需校验时间格式与开始早于结束，记录修改人和前后值。
4. 停用空间或座位不删除关联历史记录。

## 4. M2：整间教室申请与审批

### M2-01 提交申请

申请人选择有权访问的教室、开始/结束时间和用途，提交后得到申请编号。申请包含申请人、教室、时段、用途、当前审批级别、状态和审批期限。

**验收条件**

1. 校验申请人权限、教室开放状态、院系范围、开放时间、整点规则、同日规则和冲突。
2. `pending` 申请不占用座位，不能仅凭申请提交就阻止 M1 预约。
3. 申请人能查询本人状态；审批人能查询被授权范围内的待办。

### M2-02 分级审批

申请按当前级别由获授权审批人处理。一级通过后进入下一级；任一级驳回后结束并通知申请人。任务书要求多级审批，但真实审批级数、审批人和超时政策需小组与老师/管理方确认；当前代码按两级演示。

**验收条件**

1. 服务端检查审批人拥有当前级别的权限；不能跳级、重复处理已结束阶段或冒用其他级别权限。
2. 保存每级审批人、决定、意见和时间。
3. 超过审批期限仍未完成的申请转为超时撤销状态，通知申请人，且不占用座位。
4. 最终批准前再次检查当前开放时间和跨模块占用，避免申请等待期间状态已变化。
5. 只有最终批准成功后才创建带 M2 来源的整室占用；批准、审批历史、占用、审计和通知应处于同一成功事务中。
6. 发生冲突时，申请不应被错误标记为批准，也不应留下部分占用；处理冲突后可按约定重试。
7. 申请人取消未完成申请后停止后续审批；取消已批准申请时释放对应占用。

## 5. M3：物业报修工单

### M3-01 上报和派单

学生或获授权人员可针对一个座位或整个空间上报故障，填写标题、描述和等级。管理员派给有效维修人员，或由具有权限的维修人员认领。

**验收条件**

1. 一张工单明确指向一个座位或一个空间；至少填写可理解的问题描述。
2. 只有具备报修权限的用户可创建工单；只对有派工权限的用户开放派单。
3. 工单记录报告人、目标资源、问题描述、等级、状态、处理人和 SLA 截止时间。
4. 当前默认 SLA 为 24 小时、逾期通知管理员；具体等级、时限、升级接收人由小组/管理方确认。

### M3-02 维修、占用和验收

工单进入维修中时，目标座位或整间空间从对应时段的可预约结果中下架。维修完成不代表资源已经恢复，必须验收后释放维修占用。

**验收条件**

1. 只有有效的维修处理人或管理员可开始/提交维修完成。
2. `submitted → assigned → in_repair → resolved → accepted` 的状态变更符合权限和顺序；维修开始前可按规则取消，维修中不能直接删除工单。
3. 座位故障只占用指定座位；整室故障占用该空间内所有座位。
4. 维修中和等待验收期间，M1 查询须显示 M3 来源和工单号，并拒绝新预约。
5. 报修人或授权管理员验收后按同一工单号释放占用；既有业务历史不删除。
6. 工单超过 SLA 后发送一次升级通知并记录审计；重复任务不得重复升级。
7. 验收完成后，报修人可按规则评分和留言；重复评价应拒绝。

## 6. D：共享公共能力

### D-01 身份和 RBAC

账号凭据、角色、权限和部门范围由公共层提供。身份认证只确认“谁在操作”；权限检查决定“此人能否对这个对象做这件事”。

### D-02 空间与座位主数据

公共层维护空间编号、名称、区域、类型、所属院系、可见范围、容量、开放时间和启用状态；座位维护编号、所属空间、电源/无障碍标记和启用状态。M1、M2、M3 应引用同一套编号，不自行复制一套空间主数据。

### D-03 通知、审计和参数

1. 站内通知是默认渠道；SMTP 是可选外发渠道。外发失败不能回滚已经完成的业务事务。
2. 同一业务事件使用稳定唯一键防止重复通知。
3. 重要状态变化记录操作者、动作、对象编号、时间和必要的前后值；不得把密码、原始令牌或邮件凭据写入审计日志。
4. 系统可调整的预约上限等参数由管理员权限保护，并记录修改人和时间。

## 7. 跨模块集成验收

| 场景 | 操作 | 期望结果 |
| --- | --- | --- |
| M2 → M1 | 申请整间教室，先一级通过，再终审通过 | 一级通过时座位仍可约；终审后该教室在批准时段全部座位不可约，并显示申请单号 |
| M2 驳回/超时/取消 → M1 | 结束申请 | 不留有效 M2 占用；查询可说明座位当前状态 |
| M3 → M1 | 报修整室并进入维修中 | 整间空间座位不可约，显示 M3 和工单号 |
| M3 验收 → M1 | 验收维修完成 | 只释放该工单创建的占用；其他预约和占用照常保留 |
| 并发冲突 | 两个用户同时预约同一时段，或预约与整室占用同时发生 | 最终只允许一方成功；不得出现双重占用 |
| 网络调用 | M2 终审通过调用 D 资源服务 | 能观察到真实 HTTP 请求，并能从 M1 看到写回的占用来源 |

## 8. 工程与质量要求

### 8.1 小组与模块

- 项目组约 6 人；至少划分 3 个模块组，每组认领一个模块。M1/M2/M3 是业务模块，D 公共层的责任人或拆分方式由项目组讨论。
- 项目组共同使用本组开发、测试和生产环境；项目组是环境与评级单位，模块组是开发与分工单位。
- 组内分工必须记录到真实成员、实际工作和评审责任，不能把 AI 草稿描述成某成员已经完成的人工贡献。

### 8.2 人机协作与版本管理

1. 需求基线能追踪到代码入口、测试场景和未完成项。
2. 机器可读的项目约束（例如 `AGENTS.md`）随代码版本管理。
3. AI 任务先界定范围和验收标准；AI 生成的改动由对应成员审查和验证后才签收。
4. 代码、文档、迁移、初始化数据和流水线随任务分批提交；提交信息说明对应任务和原因，避免到最后一次性提交大批无法审查的改动。
5. 分支与合并策略明确。变更经 PR 评审后合并，冲突由成员处理，不交由 AI 自行合并。
6. 跨模块、公共层和 schema 变更要由受影响负责人评审；测试失败时不得进入后续部署阶段。
7. 部署版本必须有 tag，可从运行版本回溯到提交，并说明该版本包含的改动。
8. AI 对话不能替代 Git 提交历史；Git 历史需要真实反映项目进展。

### 8.3 数据、流水线与发布

1. Schema 变更用迁移脚本管理，可从空库重放；不靠人工直接改库。种子数据要脚本化、幂等，并与业务数据区分。
2. 提交和 PR 自动构建/测试；测试失败时流水线停止，不进入部署。
3. 测试环境流水线自动部署，覆盖本组所有模块；部署和集成测试要有窗口或等效协调办法，减少并发部署造成的误报。
4. 生产发布需人工审批；发布前有备份，发布后能确认当前版本，并保留回退步骤和数据风险说明。
5. 同一项目组独占自己的生产环境；组内各模块发布顺序须协调。
6. 测试不仅断言固定值，还要通过真实业务行为验证。课程要求可用“故意破坏实现，看测试是否失败”检查测试有效性。

### 8.4 评审节点交付

任务书不规定统一完成日期，由各组自行安排，但各阶段产物要可检查：

| 节点 | 必须能展示/说明的内容 |
| --- | --- |
| 项目启动 | 完成分组；各模块组认领模块；组内分工；确定 D 公共层归属方案并写决策记录 |
| 第一次 Review | 需求基线；任务拆解与依赖；架构搭建和第一次迭代功能；项目规则文件与 AI 协作方式；风险识别 |
| 第二次 Review | 主功能完成；跨模块链路打通；集成测试通过；schema 迁移进入流水线；演示提交到部署流程；说明质量保证手段 |
| 期末展示 | 完整功能演示；说明人机协作、工程实践和真实伦理取舍 |

### 8.5 期末必须现场演示

1. 从全新环境开始，通过流水线部署。
2. 提交一次经人工验收的变更，观察构建与测试自动触发。
3. 执行一次包含 schema 变更的部署，说明数据如何演进；可从历史版本中选择。
4. 演示一次生产环境发布和回退。
5. 演示一条跨模块链路：模块 A 通过网络调用模块 B，展示写回状态。
6. 若决定实施附加 Agent，再演示一次真实自然语言会话驱动的业务操作。

### 8.6 工程伦理

系统开发各阶段都要识别和处理伦理问题，不把伦理分析留到项目结束后补写。每位成员在个人课程论文中，应结合本人实际参与的工作，说明团队遇到或识别的伦理问题、采取的应对、仍存疑之处；分析应基于真实项目过程。

## 9. 待小组确认的规则

下列项不能由代码或 AI 草稿自动决定：

- D 公共层由谁承担、如何平衡工作量、公共接口由谁评审、故障由谁牵头。
- 是由一个 FastAPI 模块化单体承担全部业务，还是将某个公共能力拆成独立进程；选择理由和运行代价。
- 教室审批的级数、审批角色、审批期限和特殊教室规则。
- 预约提前天数、取消截止点、同一学生可否预约重叠时段、违约申诉和记录保留期限。
- 报修等级、SLA、升级接收人和验收人。
- 学校身份认证、通知渠道、真实用户数据范围、日志保留、部署环境和生产责任人。
- 是否实施附加 Agent；若实施，是否选择 DSH，以及谁维护部署和验收。

讨论结果应写入 `docs/decision-record.md`，补上参与人、日期、意见、决定、理由、负责人、对应提交/PR 和复核日期。
