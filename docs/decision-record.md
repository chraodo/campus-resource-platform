## 会前议案（不是已通过决定）

建议由成员 D 牵头维护公共接口和服务；成员 A/B/C 分别拥有 M1/M2/M3 业务规则。各业务模块经公共占用服务记录资源、起止时间、模块和来源单号；不由 D 单方面决定业务处罚、审批和维修验收政策。公共 API 或数据结构变化需要 D 和受影响模块 owner 一起审查。

## 选择依据

- 课程任务书要求 M1/M2/M3 共享 D，并要留下职责归属、工作量平衡和接口治理的书面结论。
- 账号、空间、通知与审计由三个模块共同依赖，统一接口可避免重复身份/资源状态。
- 每个模块保留业务决定权，避免公共层负责人代替业务负责人决定模块政策。
- D 工作可能偏重；可减少首轮范围、分配公共层不同子任务，并由 E 组织端到端测试。

## 可讨论方案

| 方案 | 好处 | 需要解决的问题 |
| --- | --- | --- |
| 一人牵头 D，各业务 owner 负责本模块（会前建议） | 公共接口一致、业务责任清楚 | D 工作量可能偏高；必须安排接口评审和备份 |
| 把 D 拆成账号、资源、通知/审计等几部分 | 单人压力较小 | 需要一位接口协调人，避免几套契约不兼容 |
| 各业务模块分别做自己的公共能力 | 模块短期内自主 | 身份、资源状态、审计会重复，跨模块冲突更难处理 |
