## 可直接照着讲的核心话术

### 开场与任务范围

“老师好，我们今天做的是项目启动评审。我们先按任务书把项目拆成四块：M1 是自习座位查找、预约和签到；M2 是整间教室申请和审批；M3 是物业报修和维修验收；D 是三块共用的身份权限、空间目录、通知和审计。任务书里的自然语言 Agent 是附加项，DSH 只是可以考虑的接入方式，不是核心系统前提。”

### 代码结构

“代码分成几处：`backend/campus_app/routers/` 是 M1、M2、M3 和公共接口；`backend/campus_app/domain.py` 放多个页面共用的业务规则；`backend/migrations/` 管数据库版本；`backend/tests/` 测试预约、审批、报修和跨模块占用；`demo/` 是网页和房间签到屏幕；`docs/requirements.md` 把任务书要求和实现、验证方式对应起来。”

### 展示业务规则

“座位查询不只看个人预约，还看整教室审批和维修单。最终一级、二级都通过后，M2 才锁全室；工单进入维修中后 M3 才下架相关空间；验收后按原工单释放。每条占用都有模块和来源单号，所以管理员能解释座位为什么不能预约。”

### 诚实说明当前进度

“我们已由 coding agent 生成核心代码初稿，并对 API 的实际业务行为跑了自动化测试；它现在不是只画页面的原型。GitHub 仓库已公开，组员可以直接查看；代码仍需小组人工逐项审查和签收。GitHub Actions 已通过代码检查、13 条测试、空库迁移、Compose 测试环境和冒烟流程；生产部署仍未进行。今天要确认负责人、规则边界和后续审查安排。”

### 分工与 D 决议

“我们建议 A 管 M1 需求与验收，B 管 M2，C 管 M3，D 管共享层和接口协调，E 组织测试与发布，F 负责评估附加 Agent。这里说的‘负责’主要是拆任务、审查和验证；代码可以由 agent 起草。现在只是建议，请组员确定真实姓名和是否接受。D 由一人牵头还是拆分给多人，今天也请大家讨论，并把决定写入记录。”

## 老师可能问的问题

**问：你们目前做了多少？**

答：“核心业务已有可运行代码初稿和自动行为测试，包括座位预约、审批、维修、共享权限和占用追溯。GitHub Actions 的 CI 和临时测试环境已通过，但代码尚未经过全组人工审查，真实邮件服务和生产部署也未验证；我们会把代码完成度和人工验收状态分开报告。”

**问：六个人具体怎么分工，怎样避免有人重复或没人负责？**

答：“我们提议 A 负责 M1 需求和验收，B 负责 M2，C 负责 M3，D 负责公共服务和接口协调，E 负责测试与交付记录，F 先组织是否做附加 Agent 的讨论；如果不做，F 整理演示和 AI 使用记录。每个模块负责人都要亲自审查自己模块的规则和测试；E 组织测试但不替模块负责人签收。这是待组员确认的方案，不代表已经认领或完成。”

**问：任务书里的内容分别对应哪里？**

答：“`docs/requirements.md` 逐条对应 M1、M2、M3、D 和工程要求；`docs/architecture.md` 解释模块与数据流；代码目录和测试入口写在 README 和本讲稿里。未确定的规则仍列为待讨论。”

**问：为什么 PR 提议把 D 资源能力拆成独立进程？**

答：“这是 PR 里的一个候选方案：M1、M2、M3 仍共享同一套代码和数据库，M2 终审通过 HTTP 调用 D 资源进程，可以作为期末跨模块网络调用演示。它会增加一个进程和部署配置，所以我们还要由小组比较模块化单体等方案，讨论后把选择和理由记入 AD-001。目前不能把这个提案说成全组已经决定。”

**问：教室申请和维修会不会跟个人预约冲突？**

答：“三类操作都会检查同一资源占用记录。待审批教室不锁座位；最终批准才锁；维修开始才下架；验收或取消后释放原记录。对应规则有 API 行为测试。”

**问：Agent 是必做的吗？DSH 和项目有什么关系？**

答：“任务书把自然语言 Agent 列为附加项。核心系统不依赖 DSH。小组若投票决定做，由 F 牵头，适配器只能通过公开 API；插件当前没有安装或运行。”

**问：怎样避免 AI 生成错代码？**

答：“每个模块 owner 先写清需求和验收条件，再读代码、运行测试并给修改意见；权限、迁移和跨模块变更要额外审查。AI 输出不等于组员签收，失败证据也要留下。”

**问：邮件提醒现在能发吗？**

答：“业务通知和 worker 已实现；SMTP 代码也在，但我们没有课程邮箱服务账号，所以外发邮件未实测。没配置时系统仍保留站内提醒；正式使用前要由小组提供并测试邮件环境。”

**问：你们怎样处理未签到和隐私？**

答：“目前只记录一次未签到，不自动累计更重处罚；签到使用按房间/日期生成的码。申诉、数据保留时长和管理员可见范围还需要老师或场地管理员确认。”

**问：CI 和部署现在工作了吗？**

答：“GitHub Actions 的 CI 和临时 Compose 测试环境已经通过；生产发布工作流只是模板，尚未运行，也没有生产主机或 self-hosted runner。”
