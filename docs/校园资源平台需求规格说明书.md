# 2. 产品概述与范围

## 2.1 产品愿景

为校园自习空间和公共教室提供一个统一入口：用户可以知道空间是否可用、按规则申请或预约、及时获得状态通知；审批人和维修人员按各自权限处理任务；管理人员维护空间和账号；所有跨模块占用都能说明来源，减少“一个模块认为空闲、另一个模块已经占用”的情况。

## 2.2 核心目标

- 预约前能查到座位和时段；预约写入时再次检查冲突，避免只相信页面上的旧查询结果。
- 整间教室只有最终审批通过后才占用；审批中的申请不会提前封锁座位。
- 维修开始后相关座位或整间空间不可新约；只有验收后才释放维修占用。
- M1、M2、M3 使用同一份空间和座位编号，并能追溯资源被占用的业务来源。
- 账号、角色、部门范围和管理操作由服务端校验，并通过通知、审计和版本记录保留必要过程。
- 课程交付可以从代码目录定位需求、API、数据模型、迁移、测试和演示入口。

## 2.3 当前范围

| 范围 | 包括 | 当前说明 |
| --- | --- | --- |
| 核心 M1 | 座位筛选、预约、本人历史、签到、取消、未签到释放、管理员预约视图 | 实现于 FastAPI 主服务；默认时长 4 小时，可由系统管理员调整。 |
| 核心 M2 | 整教室申请、两级审批、驳回、超时、取消、最终审批后占用整室 | 终审会通过 HTTP 调用资源服务；当前规则为两级、默认 24 小时超时。 |
| 核心 M3 | 座位/整室故障上报、派单、维修开始、完成待验收、验收、评价、超时升级 | 默认 SLA 24 小时；严重等级目前不自动改变 SLA。 |
| 共享 D | 认证、RBAC、空间和座位目录、参数、通知、审计 | 业务模块共用模型与数据库；资源服务进程属于现有部署组成。 |
| Web 界面 | 学生操作页、审批与维修操作、管理配置、房间签到屏 | 目录 demo/；行为最终以 API 及服务端规则为准。 |
| 可选适配接口 | Agent 写操作预览和确认入口 | 有后端预览/确认代码；没有实际自然语言 Agent 或 DSH 集成可据此宣称。 |

## 2.4 当前不作为核心交付的内容

- 真正接入自然语言大模型、DSH 插件、工具调用平台或外部智能体运行时。
- 微信、短信、学校统一身份认证等外部渠道；当前邮件依赖 SMTP 配置，外部身份源未接入。
- 收费、支付、退款、跨校区结算、跨日预约、跨时区规则。
- 另建一套独立的审批工单服务、共享信息服务或服务间令牌体系；目前 D 资源进程是同一仓库、同一数据库中的 HTTP 服务。
- 尚未通过小组讨论确认的申诉、黑名单、预约提前天数、保留期限、人工冲突强制覆盖等政策。

# 3. 术语、参与者与环境

| 术语 | 通俗解释 |
| --- | --- |

| 半开时间段 | 开始时刻算在使用时间里，结束时刻不算。例如 10:00–11:00 和 11:00–12:00 首尾相接，不互相冲突。 |

| 待验收 | 维修人员已经标为完成，但报修人还未确认；资源仍按维修中处理。 |

## 3.2 使用环境

- 前端：现代浏览器访问 Web 页面；开发环境主入口为 http://127.0.0.1:8000，接口说明在开发模式的 /api/docs。
- 后端：FastAPI 主 API；M2 最终批准由单独资源服务处理；worker 独立轮询后台任务。
- 开发数据：默认 SQLite；Compose 环境使用 PostgreSQL 17；Alembic 负责数据库表结构演进。
- 演示数据：本地可以使用虚构账号；生产环境必须关闭演示种子账号和虚构数据。

| 编号 | 规则 | 当前产品行为/基线 |
| --- | --- | --- |

## 5.1 权限检查的基本要求

- 每个 API 请求应先确认账号/凭据仍有效，再检查操作所需权限。
- 记录归属、对象范围和角色权限同时适用；例如“本人取消”也需要具备 cancel_own 权限。
- 前端不显示某按钮只能改善体验，不能代替服务端权限验证。
- 院系专属空间的访问同时检查用户部门和空间部门；空间管理员可按权限维护。
- 角色被停用或权限被撤回后，下一次请求应按最新权限拒绝不再允许的操作。
- API 错误信息不应暴露其他用户是否存在、密码摘要、凭据明文或内部堆栈。

# 6. 功能需求：账号、权限与公共服务 D

### D-AUTH-01  登录、退出和当前身份

| 优先级 | 责任模块 | 当前状态 |
| --- | --- | --- |
| P0 | D 公共能力 | 代码已实现（待人工验收） |

目标：让用户使用账号密码进入系统，后续操作可被识别为该账号。

前置条件：用户账号已建立且处于启用状态；服务端配置了安全密钥。

主流程：用户提交用户名和密码 → 服务端校验账号状态和密码摘要 → 成功后签发会话凭据 → 页面可查看本人基本资料 → 用户可退出并使会话失效。

业务规则：用户名不区分业务角色；认证成功不自动代表用户能做所有操作。会话/API token 保存哈希，不保存原始令牌；个人令牌有到期时间。

异常与边界：账号不存在、密码错误、账号停用或凭据过期时拒绝；不返回密码摘要和原始存储信息。

验收条件

- 正确账号能取得当前身份资料；错误口令无法登录。
- 停用账号不能继续调用受保护接口。
- 退出后旧会话不能继续访问业务 API。
- GET /me 只返回公开资料，不返回密码或令牌。

- 审批阶段和已作出的决定可解释。

### M2-DECISION-01  执行当前级别的批准或驳回

| 优先级 | 责任模块 | 当前状态 |
| --- | --- | --- |
| P0 | M2 | 代码已实现（两级逻辑待人工验收） |

目标：确保每级审批由具有相应权限的人作出，并留下可追踪决定。

前置条件：申请为 pending 且未到 timeout_at；审批人具有 classroom:approve 和当前阶段权限。

主流程：审批人打开申请详情 → 输入 approve/reject 与可选意见 → 服务端锁定/校验申请状态和阶段 → 写唯一阶段审批记录 → 通过时进入下一阶段，驳回时状态 rejected 并通知申请人。

业务规则：decision 只能 approve 或 reject；意见最长 500 字；阶段决策对每个申请每级唯一；一级通过通知二级审批人。

异常与边界：重复处理、越级审批、无权限、已结束、超时申请均拒绝；拒绝后不创建资源占用。

验收条件

- 审批记录包括阶段、审批人、决定、意见和时间。
- 一级批准后状态仍 pending 且 current_stage=2。
- 任一阶段驳回后申请终止，且 M1 可在该时段继续预约。

### M2-FINAL-01  最终批准后调用资源服务并占用整室

| 优先级 | 责任模块 | 当前状态 |
| --- | --- | --- |
| P0 | M2/D resource | 代码已实现（部署链路需验收） |

目标：让最终审批与跨模块资源状态同步，杜绝审批成功但座位仍被认为空闲。

前置条件：申请处于等待第二级审批；二级审批人有效；资源服务可从主服务访问；数据库版本/连接兼容。

主流程：二级审批人最终批准 → 主服务通过 HTTP PUT 调用内部资源服务 → 资源服务重新验证用户和权限 → 锁申请/空间并重新查冲突与到期 → 同一数据库事务保存第二级审批、申请 approved、M2 ResourceHold、通知和审计 → M1 后续搜索显示整室占用及申请来源。

业务规则：终审前再次查整个房间内任意个人预约或 M2/M3 占用；资源服务拒绝公网暴露；冲突返回 409；资源服务无响应返回服务不可用；相同审批人和备注可安全重试。

异常与边界：已审批后响应丢失时，调用方先刷新申请状态；只允许源申请释放自己的 hold；终审和 hold 不得只完成一半。

验收条件

- 日志或运行观察能看到真实 HTTP PUT。
- 最终通过后房间全部座位在重叠时段不可约，并返回 M2 来源单号。
- 一级通过但终审前仍没有 M2 占用。
- 终审时发现冲突不能错误标为 approved。

### M2-TIMEOUT-01  超时撤销申请

| 优先级 | 责任模块 | 当前状态 |
| --- | --- | --- |
| P1 | M2/worker | 条件性实现（需要 worker） |

目标：在审批流程长时间无人处理时结束申请，避免陈旧待办。

前置条件：申请为 pending；worker 运行；当前时间不早于 timeout_at。

主流程：后台任务找到超时申请 → 将其设为 expired → 通知申请人 → 写必要审计 → 保持没有有效房间占用。

业务规则：默认 APPROVAL_TIMEOUT_HOURS=24；这是部署参数，不是当前管理页面可调参数；以实际环境配置为准。

异常与边界：worker 停机时允许延迟，重启后补处理；对已处理申请不重复超时。

验收条件

- 过期申请状态能在申请人历史中看到。
- 过期不会留下有效 M2 hold。
- 重复任务不生成重复超时通知。

### M2-CANCEL-01  取消本人待审或已批准申请

| 优先级 | 责任模块 | 当前状态 |
| --- | --- | --- |
| P1 | M2 | 代码已实现（规则需确认） |

目标：让申请人撤回不再需要的整室申请并释放它创建的占用。

前置条件：本人申请仍 pending 或 approved；请求人拥有 cancel_own，或具有相应管理权限。

主流程：用户请求取消 → 系统检查当前状态及权限 → 写 cancelled → 若先前已批准，则仅停用来源为该申请的 M2 hold → 写审计并通知相关方。

业务规则：不能取消 rejected、expired、cancelled 申请；已经发生的审批记录保留。

异常与边界：取消和终审并发时必须锁定/检查申请，不能一边取消一边写出有效占用。

验收条件

- pending 取消不会生成 hold。
- approved 取消只释放当前申请的 M2 hold。
- 其他来源和其他时段的占用不变。

# 9. 功能需求：M3 物业报修

### M3-REPORT-01  提交故障工单

| 优先级 | 责任模块 | 当前状态 |
| --- | --- | --- |
| P0 | M3 | 代码已实现（待人工验收） |

目标：让用户报告座位或空间故障，并提供可分派处理的信息。

前置条件：用户有 work_order:create；目标资源存在且有效。

主流程：选择一个座位或一个空间 → 填标题、描述、严重程度 → 服务端验证只能选一个目标 → 创建 submitted 工单并生成到期时间 → 返回工单号。

业务规则：title 4–160 字；description 10–3000 字；severity 为 low/normal/high/urgent；当前默认 SLA 24 小时，各严重级别没有独立 SLA 配置。

异常与边界：同时选择座位和空间、两者都不选、目标不存在、文本长度不合规时拒绝。

验收条件

- 一张工单只有一个目标。
- 列表中能看见工单号、标题、目标、状态、严重程度、报告人和时间。
- 创建后可按权限查询，且未开始维修前不创建维修占用。

### M3-LIST-01  查看本人或授权工单

| 优先级 | 责任模块 | 当前状态 |
| --- | --- | --- |
| P1 | M3/D | 代码已实现（待人工验收） |

目标：让报修人跟踪自己工单，让维修和管理角色获取其工作范围内工单。

前置条件：用户有 work_order:read_own 或 work_order:read_all。

主流程：按时间/状态查看工单 → 普通用户仅看到本人 → 维修/运营角色按其权限看全部可处理工单。

业务规则：工单保留状态、责任人、SLA 时间、评价和目标信息；接口响应不返回凭据字段。

异常与边界：越权查询他人工单拒绝；已取消工单不可被误列为正在维修任务。

验收条件

- 维修人员可以找到被分配或可认领的工单。
- 报修人可以看到自身处理进度。
- 用户不能通过猜测工单编号读取未授权记录。

### M3-ASSIGN-01  派单、改派或认领工单

| 优先级 | 责任模块 | 当前状态 |
| --- | --- | --- |
| P1 | M3/D | 代码已实现（需核对权限细节） |

目标：将故障任务明确分配给有维修能力的人员。

前置条件：工单仍可分派（submitted 或 assigned）；操作者有派工权限；目标维修人员有效且具有维修角色。

主流程：有 assign:any 权限的管理者指定维修人，或维修人员按当前规则认领 → 保存 assignee_id → 状态设 assigned → 更新工单与通知。

业务规则：不同权限区分“为自己认领”和“派给其他人”；重复指派应可解释，并保留更新审计。

异常与边界：工单已开始/完成/取消、目标维修账号无效或无派工权限时拒绝；操作失败不应覆盖原 assignee。

验收条件

- 派工后列表能显示维修责任人。
- 只有有效维修角色可开始处理。
- 无派工权限用户不能把工单转给任意账号。

### M3-START-01  开始维修并阻止相关资源新预约

| 优先级 | 责任模块 | 当前状态 |
| --- | --- | --- |
| P0 | M3/D | 代码已实现（并发需重点验收） |

目标：维修实际开始时，把故障座位或空间从同期可预约资源中暂时排除。

前置条件：工单状态为 assigned；当前用户为指派维修人员或有管理权限。

主流程：维修人员开始工单 → 系统检查状态、目标和责任人 → 状态变为 in_repair → 创建来源为该工单的 M3 ResourceHold → 写审计/通知。

业务规则：座位报修只封锁座位；空间报修覆盖房间内所有座位；维修 hold 当前使用远期结束时间，直到验收释放。

异常与边界：重复开始、未派单开始、无权限开始时拒绝；若该空间已有预约/整室占用，需要按规则处理并记录冲突，不能静默覆盖。

验收条件

- M1 搜索显示 M3 来源和工单号。
- 仅该目标资源受影响，不扩大到其他空间。
- 维修中和 resolved 待验收期间仍不可预约。

### M3-RESOLVE-01  提交维修完成并等待验收

| 优先级 | 责任模块 | 当前状态 |
| --- | --- | --- |
| P1 | M3 | 代码已实现（待人工验收） |

目标：区分“维修人员做完了”和“使用者确认可以恢复使用”。

前置条件：工单状态为 in_repair；操作者有 repair 权限且是有效处理人/管理员。

主流程：维修人员提交完成 → 工单状态变 resolved → 给报修人发验收提醒 → M3 hold 保持 active。

业务规则：标记完成不自动释放资源；验收人需要看到工单说明与完成状态。

异常与边界：未开始维修或已终态工单不能标完成；通知失败不应丢失 resolved 状态。

验收条件

- resolved 工单仍会阻止新预约。
- 报修人能收到待验收通知或在页面看到状态。
- 完成操作写审计。

### M3-ACCEPT-01  验收维修并释放占用

| 优先级 | 责任模块 | 当前状态 |
| --- | --- | --- |
| P0 | M3/D | 代码已实现（待人工验收） |

目标：由报修人或授权管理员确认维修完成，并只释放这张工单创建的资源占用。

前置条件：工单为 resolved；操作者是 reporter 或有管理权限。

主流程：验收者确认 → 状态变 accepted → 按来源工单号停用所有 active 的 M3 hold → 写审计并通知维修人员。

业务规则：当前 API 是肯定验收，没有“拒绝验收/退回维修”分支；如课程需要退回，需要新增产品规则和状态。

异常与边界：未 resolved 时不能验收；非报修人且无管理权限者拒绝；重复验收拒绝。

验收条件

- 验收后可预约性恢复，前提是无其他占用。
- 只释放该工单产生的 hold，不影响其他工单或 M2。
- 接受状态保留工单历史。

### M3-RATING-01  报修人评价维修结果

| 优先级 | 责任模块 | 当前状态 |
| --- | --- | --- |
| P2 | M3 | 代码已实现（待人工验收） |

目标：收集维修服务评价，帮助后续运营改进。

前置条件：工单状态 accepted；操作者为 reporter；工单尚无评价。

主流程：报修人提交 1–5 分评分和可选文字 → 服务端存 rating/comment → 写审计。

业务规则：当前评分范围 1 到 5；评论最多 500 字；每张工单只允许评价一次。

异常与边界：未验收、他人评价、评分越界、重复评价时拒绝。

验收条件

- 只有已验收工单才能评价。
- 评分和留言与工单编号对应。
- 重复请求不会覆盖既有评价。

### M3-SLA-01  维修超时提醒和升级

| 优先级 | 责任模块 | 当前状态 |
| --- | --- | --- |
| P1 | M3/worker/D | 条件性实现（需要 worker） |

目标：对超出当前处理时限的工单提醒管理员关注。

前置条件：worker 正常运行；工单状态仍为 submitted、assigned 或 in_repair；当前时间已到 due_at。

主流程：worker 检查到期工单 → 设置 escalation_sent → 通知启用的 admin 账号 → 写系统审计 → 后续轮询不再重复升级。

业务规则：默认 WORK_ORDER_SLA_HOURS=24；按当前实现，超期通知管理员，不按 low/normal/high/urgent 区分时限。

异常与边界：邮件失败不阻止站内升级通知；resolved/accepted/cancelled 不继续升级；worker 暂停时处理会延后。

验收条件

- 一张工单最多升级一次。
- 超时升级能在后台通知/审计中追踪。
- 处理完成或取消后的工单不继续升级。

### M3-CANCEL-01  维修开始前取消本人报修

| 优先级 | 责任模块 | 当前状态 |
| --- | --- | --- |
| P2 | M3 | 代码已实现（规则需确认） |

目标：让报修人撤回尚未进入维修的错误或重复报修。

前置条件：工单为 submitted 或 assigned；操作者为 reporter 或有相应管理权限。

主流程：报修人取消 → 状态设 cancelled → 记录审计和通知 → 若尚未开始维修则不存在活跃 M3 hold。

业务规则：维修已开始后不能通过普通取消删除工单；必须走维修完成/验收流程。

异常与边界：in_repair、resolved、accepted 或已经取消的工单不能直接取消。

验收条件

- 取消后工单历史仍可见。
- 取消不会影响同目标的其他工单。
- 已开工时系统拒绝普通取消。

# 10. 跨模块集成与共享资源约束

## 10.1 共享占用规则

M1 查询可预约性时，必须综合个人预约记录和 M2/M3 的资源占用记录。业务模块只能按各自规则建立或释放其来源的记录，不能直接清理另一个模块的占用。

| 来源 | 记录在哪里 | 何时开始占用 | 何时释放 |
| --- | --- | --- | --- |
| M1 个人预约 | Reservation 本身 | 预约创建成功进入 confirmed；签到后变为 checked_in，并持续占用该座位至预约结束。取消或未签到超时后释放。 |
| M2 整室审批 | ResourceHold：module=M2、resource_type=room | 二级审批最终成功时 | 申请取消；来源申请的 hold 被停用。 |
| M3 座位维修 | ResourceHold：module=M3、resource_type=seat | 工单进入 in_repair | 报修人/授权管理员验收后。 |
| M3 整室维修 | ResourceHold：module=M3、resource_type=room | 工单进入 in_repair | 报修人/授权管理员验收后。 |

## 10.2 防止冲突与信息错乱

- 时间重叠采用 A.start < B.end 且 A.end > B.start；正好结束后开始不算冲突。
- 预约与最终批准都必须在写入时重新查冲突，不能依赖先前查询。
- 所有占用记录都要有模块、来源单号、资源类型/编号、时间、理由和 active 状态。
- M2 整室规则覆盖房间内每个座位；M3 座位和整室故障覆盖范围不同。
- 业务状态、占用、通知和审计应尽量在同一个数据库事务里提交；邮件作为外部副作用异步发送。
- 取消、超时、完成、验收都是状态变更，不物理删除业务历史。
- 同资源并发写入需要一致的锁定/事务策略。当前仓库已有 SQLite 写事务串行化与 PostgreSQL 房间行锁；座位停用与并发预约仍是需要复核的风险。

## 10.3 M2 资源服务调用契约

| 项目 | 要求 |
| --- | --- |
| 调用入口 | 主服务调用内部 PUT /internal/v1/classroom-holds/{application_id}。 |
| 调用前 | 主服务确认当前操作来自有效会话；不要将内部接口作为浏览器公开入口。 |
| 资源端验证 | 资源服务重新认证凭据，检查审批阶段/权限、超时、房间状态和冲突。 |
| 成功结果 | 审批记录、申请 approved、M2 room hold、通知、审计一致提交。 |
| 冲突结果 | 返回冲突并保持申请未错误批准，不产生遗留 hold。 |
| 网络失败 | 主服务返回可理解的临时失败；用户刷新当前申请状态后再决定是否安全重试。 |
| 部署安全 | 资源进程只留在受信应用网络；跨主机传输凭据使用 HTTPS；不要把内部端口暴露公网。 |

## 11.1 通用交互要求

- 提交前展示关键字段摘要；写操作需明确按钮文案，避免把“保存草稿”误作“正式提交”。
- 后端拒绝请求时，页面提示应说明用户下一步能做什么，例如重新选时段、联系管理员或等待审批。
- 网络超时后页面不能假设操作失败或成功；需提供刷新状态的路径，防止重复创建业务记录。
- 按钮是否可见不是权限判定；后端返回 403/409 时应提供可理解的解释。
- 关键业务单号应显示并可复制，便于课堂演示和跨模块追踪。

## 12.1 数据一致性约束

- 预约用户和座位、申请人和空间、工单报告人和目标资源通过稳定 ID 关联。
- Room ID、Seat ID 作为业务引用编号，不因改显示名称而改变。
- Appointment/Reservation 记录不得与其来源占用记录混淆；目前 M1 不通过 ResourceHold 表表示个人预约。
- ResourceHold 的 source_id 必须能回到源申请或源工单；释放时只变更该来源。
- 角色权限码、状态码、工单等级等有限取值应由 schema/服务端共同校验。
- 数据库结构变化通过 Alembic 迁移；迁移需从空库可重放，生产表不应手工改结构。

# 13. 状态机与状态变化

## 13.1 M1 预约状态

创建成功 → confirmed → checked_in（按时到场）
创建成功 → confirmed → cancelled（本人取消）
创建成功 → confirmed → expired + violation=true（未在签到期限内签到）

当前代码没有“签到后自动完结”的单独状态，也没有独立申诉/撤销违约流程。是否需要这些规则由小组确认。

## 13.2 M2 申请状态与审批阶段

pending(stage=1) --一级批准--> pending(stage=2) --二级批准 + 资源服务成功--> approved
pending(stage=1 或 2) --任一级驳回--> rejected
pending --到期--> expired
pending / approved --申请人按权限取消--> cancelled

最终审批和 M2 room hold 必须保持一致；被驳回、超时、取消的申请不应有活动占用。当前代码没有附件上传或退回补材料状态。

## 13.3 M3 工单状态

submitted → assigned → in_repair → resolved → accepted
submitted / assigned → cancelled（维修开始前）

创建工单后即计算 due_at；当前升级只针对 submitted、assigned、in_repair。in_repair 和 resolved 阶段均保持 M3 占用。当前没有“验收不通过、退回维修”状态。

## 13.4 非法状态变化

- 终态记录不能被重复审批、取消、签到或验收。
- 跨级审批、跳过维修开始而直接完成、没有维修权限而认领/派单，均拒绝。
- 每次状态变化都要由服务端检查当前数据库状态，不能只依赖前端上次读取的状态。
- 并发请求只有一个能成功转换状态；另一个应收到可解释的冲突响应。

# 15. 通知、后台任务与邮件

| 后台任务 | 触发条件 | 系统行为 | 依赖/边界 |
| --- | --- | --- | --- |
| 预约开始提醒 | 预约开始前 15 分钟窗口 | 创建站内通知；可配置邮件排队。 | worker 正常运行；唯一键避免重复。 |
| 迟到提醒 | 开始后约 10 分钟且未超过 15 分钟 | 提醒用户尽快签到和释放时间。 | 已签到/取消记录不应重复提醒。 |
| 未签到释放 | 开始后约 15 分钟仍为 confirmed | 设 expired、violation=true，释放可预约性并审计。 | worker 停机后重启需补处理。 |
| 教室审批超时 | pending 且 timeout_at 已到 | 设 expired、通知申请人、不创建 hold。 | 默认配置为 24 小时；worker 依赖。 |
| 维修超时升级 | 开放工单超过 due_at 且未曾升级 | 通知启用的管理员并写审计。 | 默认 SLA 24 小时；当前不按 severity 改时限。 |
| 邮件投递 | 通知已排队且配置 SMTP | 有界重试并记录最后尝试/错误/成功时间。 | SMTP 不可用时站内通知仍然可用。 |

worker 默认轮询周期约 30 秒。生产/演示部署应确保 worker 至少有一个实例持续工作；当前说明建议避免多实例并发重复投递。作业失败应留日志并允许后续轮询恢复，不能因为邮件失败阻断预约/审批/维修。

# 16. 安全、隐私与审计

| 控制项 | 需求 |
| --- | --- |
| 身份凭据 | 密码只保存安全摘要；会话/API/屏幕凭据不能明文持久化；提供撤销/过期机制。 |
| 授权 | 每个接口做服务端 RBAC 和对象归属/部门范围校验；管理接口不能仅靠页面隐藏。 |
| 屏幕端 | 每个房间独立屏幕 token；令牌只能读取本房间每日码；回应设置 no-store；屏幕页面不含个人名单。 |
| 内部接口 | 资源服务内部接口不暴露公网；跨主机时使用 HTTPS 与受控网络；内部请求仍重新验证用户。 |
| 审计 | 只记录完成责任追踪所需字段；禁止密码、原始 token、SMTP 密码进入审计详情或日志。 |
| 个人信息 | 查询遵循最小必要；学生仅查本人；后台查询需相应权限；学校实际身份、邮件和保留策略待确认。 |
| 演示数据 | 使用虚构账号和空间；部署生产环境前禁用种子账号/演示密码并轮换密钥。 |
| 输入校验 | 时间、长度、枚举、资源目标二选一和权限都在服务器校验；前端校验只用于即时反馈。 |

## 16.1 隐私待确认

- 学校是否提供统一身份认证以及使用什么账号标识。
- 真实用户是否必须填写邮箱；SMTP/微信/短信的授权和投递策略是什么。
- 预约、工单、违约和审计保留多长时间，谁可以查询、导出或删除。
- 是否允许空间管理员看到学生身份、具体预约内容，及这些数据的最小展示范围。

# 18. 验收场景与评审演示

下面场景可以用作第一次/后续评审的检查清单。每个场景都需要准备虚构账号、样例空间、具体时段和预期结果；演示时不应把未运行过的链路说成已通过。

| AC-13 | 迁移与启动 | 用新数据库执行迁移，按 README 启动 API、resource、worker | 程序能启动，演示账号来自虚构 seed，API 文档可访问。 |

## 18.1 展示顺序建议（15–20 分钟）

- 1–2 分钟：一句话说明产品目标与 M1/M2/M3/D 边界。
- 2–3 分钟：展示目录和文件位置：README、backend/campus_app、demo、backend/tests、backend/migrations、docs。

- 4–5 分钟：演示 M2 一级/二级审批、资源服务 HTTP 调用及 M1 占用来源。
- 3–4 分钟：演示 M3 报修、维修开始、待验收、验收后释放资源。
- 2–3 分钟：回答共享数据、权限、冲突、测试、未完成政策和下一步分工。

> **诚实汇报口径** “当前仓库有这些代码；这些自动化/人工检查已实际运行；这些政策仍待讨论。”这三类说法分开讲，最容易让老师看清项目进度。

# 20. 现状、已知限制和待决策事项

## 20.1 当前代码可支持的汇报结论

- 仓库具备 M1 座位预约、M2 两级审批、M3 报修维修、D 公共能力和浏览器演示界面的代码结构。
- M1 预约与 M2/M3 资源占用共用状态查询规则；M2 终审有独立资源服务 HTTP 链路。
- worker 代码覆盖提醒、未签到释放、审批超时、工单升级和可选 SMTP 邮件。
- 自动化测试文件、数据库迁移、Compose 和 CI 文件存在；本需求文档撰写过程没有重新运行这些测试。
- README 说明过去的 CI/自动化行为检查有成功记录，但具体提交 SHA、PR 最新状态和人工验收需要另行核对。
- 生产服务器、学校身份源和正式邮件渠道没有在本文件中被假定为已部署。

## 20.2 已知实现限制/风险

| 事项 | 现状 | 处理建议 |
| --- | --- | --- |
| M2 规则 | 当前按两级审批和默认 24 小时实现；附件里更长时限和复杂补偿状态并非现状。 | 小组确认级数、审批人、期限和冲突后的业务处理，再更新需求。 |
| 预约管理政策 | 没有预约提前天数、取消截止窗口、违约申诉、同人并行上限。 | 由老师/场地管理方确认，暂时不要宣称系统已有。 |
| M3 SLA | 统一默认 24 小时、通知管理员一次；严重级别不影响 SLA。 | 确认不同等级是否有不同 SLA、升级对象与是否要退回维修。 |
| M3 验收退回 | 只有肯定验收，未实现 reject/return 流程。 | 确认课程验收是否要求退回；若需要，补充状态与责任。 |
| 共享结构 | M1 Reservation 表、M2/M3 ResourceHold 表分开；不是统一 occupancy 表。 | 演示时解释记录分离但查询规则统一。 |
| 并发停用 | 管理员停用座位和 M1 预约使用的锁策略尚未统一；存在并发窗口风险。 | 在课程验收前评估并补充一致锁策略及并发行为验证。 |
| 邮件/身份 | SMTP 仅在有环境配置时启用；学校统一认证未接入。 | 确认测试/生产凭据管理和个人信息处理边界。 |
| Agent/DSH | 后端有写操作预览/确认接口；无实际自然语言 Agent/DSH 集成。 | 当作附加项，先由小组决定是否实施，不影响核心模块验收。 |
| 正式部署 | Compose/CI 相关配置存在；生产上线与现场回退未据此证明完成。 | 单独记录环境负责人、发布批准、备份和回退演示。 |

# 附录 A. 相对参考材料的范围说明

用户提供的参考 DOCX 含有不少细化方案。为保持本规格与现有产品一致，采用以下对照原则。

| 参考材料中的设想 | 当前产品情况 | 本规格如何处理 |
| --- | --- | --- |
| M1 另设签到流水/考勤报表/违约阈值管理 | 当前 Reservation 有 checked_in_at、violation；没有独立考勤表和完整报表流程。 | 只写当前签到和违约能力；报表/申诉列待决定。 |
| 预约提前天数、取消前置窗口、同人并行数等固定政策 | 当前代码没有统一实现这些规则。 | 列为待小组/场地管理方确认，不臆定数值。 |
| M2 复杂多级、48 小时审批和 PENDING_SYNC 等状态 | 当前代码为两级审批、默认 24 小时；终审调用资源服务。 | 按现有状态和调用流程写；附件扩展状态不当作现状。 |
| M2 人工覆盖冲突、审批回滚/补偿 API | 当前没有完整的人工冲突强制覆盖业务。 | 保留“冲突必须拒绝且无半写入”验收；覆盖策略待讨论。 |
| M3 clientRequestId、多个 seatIds、退回返修 | 当前一张工单只针对一个座位或一个空间；没有请求 ID 字段或拒绝验收分支。 | 记录现有输入约束；批量报修和退回维修不在当前范围。 |
| M1/M2/M3 拆成多个独立服务、统一业务码 | 当前业务路由共享同一个 FastAPI 主应用；HTTP 状态码和 detail 为主。 | 按实际进程边界解释；不承诺附件中的独立 M1/M2/M3 服务与业务码。 |
| 统一 seat_occupancy、seat_state_log 等专用表 | 当前实体为 Reservation 与 ResourceHold，辅以业务单和审计。 | 按现有模型说明共享占用行为和来源约束。 |

> **规则优先级** 课程任务书定义项目必须交付的课程范围；项目当前代码说明仓库实际实现；参考 DOCX 用于补充讨论。若参考材料与实际代码冲突，应把差异列为待办并经小组决议后再调整产品，不把参考文字直接当成已实现功能。
